## Project Identity

- **Name**: `hao-backprop-test`
- **Purpose**: Minimal HTTP microserver used as a **Backprop integration test harness** (per `README.md` line 3 and Tech Spec §1.1.2).
- **Audience**: Developers, DevOps personnel, automated pipelines (such as Backprop), and Blitzy agents.
- **Posture**: Development/test server only — **not production-intended** (per `README.md` line 3).
- **License**: No license file is present in the repository (no license declared).

## Runtime Architecture

- **Language**: Python 3.13+ — hard requirement per Tech Spec §2.4.1 and §3.1.1.
- **Framework**: Flask 3.1.3 — with Werkzeug 3.1.x as a transitive dependency, and Jinja2, MarkupSafe, itsdangerous, click, and blinker as further transitive dependencies.
- **Active entry point**: `app.py` — a single-file microserver, 93 lines.
- **Bind**: `127.0.0.1:3000` — hardcoded in `app.py` lines 30–31 as the `HOST` and `PORT` module constants; localhost-only to prevent external network exposure.
- **No environment-variable configuration**: Runtime constants are intentionally hardcoded (Tech Spec §2.4.1). To change the host or port, edit `app.py` directly.
- **Server**: Flask's built-in Werkzeug development server, started via `app.run(host=HOST, port=PORT)` at `app.py:92–93` — **not a production WSGI server**.
- **WSGI app object**: `app` — Flask instance created at `app.py:25` via `Flask(__name__)`.
- **Route precedence**: Flask's route specificity ensures `GET /health` matches the dedicated health handler before the dynamic catch-all route is evaluated (per Tech Spec §2.1 F-001 and `README.md` line 33).

## Endpoints

| Method | Path | Status | Content-Type | Body |
|---|---|---|---|---|
| `GET` | `/health` | 200 | `application/json` | `{"status":"ok"}` |
| any accepted method | any other path | 200 | `text/plain` | `Hello, World!\n` (14 bytes, trailing newline included) |

The catch-all handler accepts seven HTTP methods, defined as the `METHODS` constant at `app.py:33`: `GET`, `POST`, `PUT`, `DELETE`, `PATCH`, `HEAD`, `OPTIONS`. `HEAD` responses are auto-derived by Flask from `GET`: the response body is empty but the Content-Type and Content-Length headers match the equivalent `GET` response (per Tech Spec §2.1 F-003). `OPTIONS` responses are auto-generated by Flask with an `Allow` header listing the methods registered for each route (per Tech Spec §2.1 F-004). The catch-all body is exactly 14 bytes — the literal string `Hello, World!\n` including the trailing newline — preserving byte-for-byte parity with the legacy runtime.

## Testability Pattern

- **Import safety**: The `if __name__ == '__main__':` guard at `app.py:92–93` prevents `app.run()` from binding the port when `app.py` is imported as a module (e.g., by the test suite or by any other caller).
- **Test client fixture**: `tests/conftest.py` defines a `client` fixture that yields `flask_app.test_client()`, giving tests in-process WSGI access without binding a real socket.
- **Fixture scope**: Function-scoped (the pytest default) — every test receives a fresh, isolated client instance with no shared state.
- **Verification framework**: `pytest` — not declared in `requirements.txt` by design; installed ad hoc in the developer or CI environment. `pytest-cov` is similarly optional and used only for line-coverage reporting.

## Commands

```bash
# Run the server (foreground; Ctrl+C to stop)
python app.py

# Run the full test suite with verbose output
python -m pytest -v

# Run tests with coverage report
python -m pytest --cov=app --cov-report=term-missing
```

On a fresh machine, the typical bootstrap is:

```bash
python3.13 -m venv venv
source venv/bin/activate            # On Windows: venv\Scripts\activate
pip install -r requirements.txt
pip install pytest pytest-cov       # Developer-only; NOT added to requirements.txt
```

Development-only tools (`pytest`, `pytest-cov`) are installed ad hoc and are deliberately excluded from `requirements.txt` per Tech Spec §2.4.1.

## Out of Scope

Per Tech Spec §1.3.2, the following are explicitly **out of scope** for this repository:

- CI/CD pipelines and GitHub Actions workflows.
- Docker, Docker Compose, Kubernetes, and production WSGI servers (Gunicorn, uWSGI, mod_wsgi).
- Authentication, authorization, TLS, rate limiting, and input validation.
- Databases, caches, message queues, and any form of persistence.
- Environment-variable-driven configuration.
- Frontend, UI, static assets, or templates — this is a headless HTTP API only.
- Performance SLAs and load-testing harnesses.
